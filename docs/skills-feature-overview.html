Skills: visual automation workflows

Skills lets operators build building-automation workflows on a drag-and-drop canvas — no driver knowledge required — and run them through PlaceOS's existing trigger engine. This document covers what shipped, how it binds to real systems and modules, and what's left.

01

The concept

Every PlaceOS deployment can already do condition→action automation through Triggers, but authoring one demands domain knowledge: which module, which status variable, which function, which arguments. Skills abstracts that away. An operator thinks in terms of capabilities — "when Occupancy is detected, turn on HVAC and Lighting" — and the builder resolves those capabilities to the concrete modules in the chosen system.

The core ideas:

  • Blocks are capabilities, not devices. The palette offers inputs (Occupancy, Motion, Temperature…) and outputs (HVAC, Lighting, Access…) by function. Which blocks are available depends on what the selected system actually contains.
  • A skill belongs to a system. You pick the system first; the skill's blocks bind to that system's modules and the skill is stored on that system.
  • Execution is delegated, not reinvented. A finished skill compiles to a standard PlaceTrigger, so the backend needs zero new surface area to run it.

Entry points: /skills in the sidebar (Automate section), and a Skills tab on each system showing that system's skills.

02

Product tour

Builder interactions worth knowing when demoing:

  • Drag palette items onto the canvas; blocks auto-bind to a matching module on drop.
  • Click a block's right connector, then another block's left connector, to draw a connection. Click a line to remove it.
  • Drag empty canvas to pan; Ctrl/Cmd+scroll zooms around the cursor; the fit button frames the whole graph; clicking the percentage resets to 100%.
  • Ctrl+Z / Ctrl+Y for undo/redo (50 steps, typing coalesced). Clearing the canvas is undoable, so it doesn't nag for confirmation.
  • Live validation runs continuously: missing inputs/outputs and cycles are errors; disconnected or unbound blocks are warnings. Run/Deploy is blocked on errors with the reasons listed.

04

Binding to systems & modules

This is the heart of the abstraction. A skill is created for a system; from that moment everything resolves against that system's modules.

Loading the system's modules

On entering the builder, loadSystemModules() calls queryModules({ control_system_id }) and converts each module into the reference format the trigger engine and exec APIs use — class name + index: 

mod = `${custom_name || name}_${index}`   // e.g. "Occupancy_1", "HVAC_2"

The index comes from calculateModuleIndex() in common/api.ts — the same helper the existing Triggers module uses — so a skill's module references are byte-compatible with hand-authored trigger conditions.

Palette availability

Each block category maps to driver/module name patterns in CATEGORY_MODULE_PATTERNS (skills.types.ts): 

'Occupancy':  ['occupancy', 'sensor', 'people counter'],
'HVAC':       ['hvac', 'climate', 'aircon', 'ac'],
'Lighting':   ['lighting', 'light', 'dmx', 'dali'],
'Notification': [],   // empty = software-only, always available
…

A category is available when any module's name or custom name contains one of its patterns. Unavailable palette items are dimmed and drag-disabled. This heuristic is only the first pass — the explicit binding below is what actually gets executed, so a wrong guess costs nothing.

The binding itself

Every input/output block carries a BlockBinding:

interface BlockBinding {
    module_id: string;      // database id, e.g. "mod-Ab12Cd"
    mod: string;            // trigger-format reference, e.g. "Occupancy_1"
    module_name: string;    // friendly display, e.g. "Meraki Scanning API"
    status?: string;        // INPUT: watched status variable, e.g. "presence"
    method?: string;        // OUTPUT: function to execute, e.g. "power"
    args?: Record<string, any>;  // OUTPUT: function arguments
}

When a block is dropped, the state service auto-resolves the first matching module and pre-fills module_id / mod / module_name (blocks saved before the module list loads are back-filled once it arrives). The operator completes — or overrides — the binding in the settings panel:

PickerBacking APINotes
Source modulequeryModules({control_system_id})Lists the system's modules as Class_N references.
Status variable (inputs)systemModuleState(system, class, index)Keys of the module's live state. Falls back to free-text entry when the module can't be queried (offline / mock).
Function (outputs)functionList(system, class, index)Shows each function with its parameter names, e.g. power(state). Same free-text fallback.
Arguments (outputs)—JSON object editor with validation; invalid JSON is rejected with an inline error and never saved.

Results are cached per module reference in signals (module_statuses, module_functions) and invalidated when the system changes. The block face always shows the resolved truth: via Meraki Scanning API on top, Occupancy_1.presence underneath — awareness without requiring domain knowledge.

05

Persistence model

Skills live in the PlaceOS backend as metadata — no new backend surface. Three layers, in order of authority:

CanonicalEach system's skills metadata entry holds that system's skills (details: SkillData[]). Skills travel with the system; shared across users.
IndexThe org zone's skills-index entry holds a denormalised copy of all skills, so the global list is one read instead of one per system.
MirrorlocalStorage caches whatever was last read/written, and becomes the store when the backend is unreachable — which is what keeps mock-mode development fully working.

A save (SkillsPersistenceService.saveSkill) does, in order:

  1. Read-modify-write the system's skills metadata via showMetadata / updateMetadata.
  2. Replace that system's entries in the org-zone skills-index.
  3. Update the localStorage mirror (always, even when the API calls fail).

The org zone is discovered once via queryZones({ tags: 'org', limit: 1 }) and cached. If no org zone exists, the index step is skipped and the global list falls back to the mirror.

Known trade-off: writes are last-write-wins with no conflict detection, and the two-write scheme (system + index) is not transactional. Fine for a v1 with few authors; see §9 for the recommended hardening.

06

Compiling to triggers

Production execution reuses the trigger engine. compileToTrigger() walks the graph and emits a standard PlaceTrigger payload:

Graph elementTrigger element
Input block (binding + threshold/condition settings)conditions.comparisons[] — { left: {mod, status, keys}, operator, right }
Condition setting (greater_than / less_than / equals)TriggerConditionOperator.GT / LT / EQ
Output block reachable from an input (graph BFS)actions.functions[] — { mod, method, args }
Logic / Agent / Communication blocksIgnored — surfaced as a compile note in the deploy dialog

The example in Fig 3 compiles to:

{
  "conditions": { "comparisons": [
    { "left": { "mod": "Occupancy_1", "status": "presence", "keys": [] },
      "operator": "greater_than", "right": 1 }
  ], "time_dependents": [] },
  "actions": { "functions": [
    { "mod": "HVAC_1",     "method": "power",     "args": { "state": true } },
    { "mod": "Lighting_1", "method": "set_level", "args": { "level": 80 } }
  ], "mailers": [] }
}

Deploy lifecycle

  1. Guards: skill must be saved, not dirty, not on the demo system; compile must yield ≥1 comparison and ≥1 function.
  2. First deploy: addTrigger() creates the parent trigger (named Skill: <name>); the returned trigger_id is persisted onto the skill immediately, before attaching.
  3. addSystemTrigger() attaches the trigger to the system; trigger_attached is then persisted. Because both ids are recorded step-by-step, a failure mid-deploy retries idempotently — no orphaned triggers, no double instances.
  4. Redeploys: updateTrigger(trigger_id) in place.

All comparisons are ANDed (the trigger default). Simulate mode is unchanged by deployment — it dry-runs the graph locally and reports what would fire, shown in a dialog.

07

The demo system

demo-system.ts defines a virtual system (sys-demo) pinned to the top of the system selector. Selecting it:

  • Generates one module per hardware-backed category directly from CATEGORY_MODULE_PATTERNS — so every palette block is active, and new categories are covered automatically.
  • Feeds the binding pickers canned data: statuses like presence, people_count, temperature; functions like power(state), set_level(level), notify(message).
  • Persists skills normally (so a polished walkthrough skill can be prepared in advance) but refuses to deploy, with a clear message.

09

Open items & loose ends

Must fix before merge

BlockerAuth guards are bypassed. authorised-user.guard.ts and authorised-admin.guard.ts currently return true for local development. Restore before this branch ships.
BlockerForced mock mode. common/placeos.ts forces mock on localhost:4200. Remove or gate behind an env flag.
BlockerNot yet run against a real backend. All metadata/trigger writes need a pilot against placeos-dev before any release; mock mode can't exercise them.

Functional gaps

OpenLogic / Agent / Communication blocks don't execute. They exist on the canvas but are ignored at compile time (with a warning). Logic AND/OR could map to trigger any_match + condition grouping; Communication maps naturally to trigger mailers; the Agent block needs a product decision (it implies an LLM-in-the-loop runtime that triggers can't express).
OpenTime Schedule inputs should compile to trigger time_dependents (cron / at). Currently they're software-only decoration.
OpenSimulate is static. The natural next step is binding input blocks to live status over the realtime websocket (getModule(...).binding(status)) and animating values through the graph — the binding data model already supports it.
OpenTrigger lifecycle is half-managed. Deleting a skill does not remove its trigger (deliberate for now, stated in the delete dialog); renames only propagate on redeploy; there's no drift detection if someone edits the trigger directly in the Triggers module.
OpenMultiple inputs are ANDed only. No OR/branching semantics yet; connection topology beyond input→output isn't reflected in compilation.

Smaller loose ends

  • Args editor is raw JSON; functionList already returns parameter names, so per-parameter typed fields are within reach.
  • Palette availability is pattern-matching on module names — good enough as a hint, but a curated capability→driver mapping (or driver metadata) would make it exact.
  • Concurrent editing is last-write-wins; consider metadata version checks (the API keeps metadata history, which could also power skill revisions/rollback).
  • The per-system Skills tab lacks the list page's duplicate/delete/toggle actions; the systems tab count badge (counts.skills) is never populated.
  • No unit or E2E tests for the skills feature yet (the repo has Vitest + Playwright ready; the capture script for this doc is a starting point for an E2E flow).
  • Canvas is mouse-only — keyboard accessibility for block manipulation was consciously deferred (lint rules disabled per the codebase's existing pattern).
  • A handful of strings in the builder are not routed through the localisation pipe yet.
  • Mobile/narrow layouts aren't designed; the builder assumes desktop.

10

Recommendations

  1. Pilot against placeos-dev next. Everything backend-facing uses standard ts-client calls, but metadata write permissions (support vs admin), org-zone discovery on real domains, and trigger attach semantics all deserve one real-environment pass before broadening.
  2. Decide the multi-tenant story for the index. One org-zone index is right for single-org installs; multi-domain deployments may want a per-domain index or server-side metadata search instead.
  3. Prioritise live simulation. It's the highest demo-value item left, it makes Simulate honest, and the websocket plumbing already exists in Backoffice (debug console uses it).
  4. Close the trigger lifecycle loop. Offer "remove trigger" on skill delete, sync names on save-when-deployed, and surface the trigger's activated_count back onto the skill card — cheap and makes deployed skills feel alive.
  5. Define the Agent block. It's the most differentiated idea on the canvas and the only one with no execution path. Options: compile to a webhook-enabled trigger that calls an agent service, or gate it behind the upcoming AI work already in the repo (driver-ai-builder, system-ai-configure).
  6. Add an E2E happy path (create → bind → save → deploy) before inviting other contributors into this code.
